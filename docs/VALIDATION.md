# SyncView 검증 기록

검증일: 2026-09-21. 이 문서는 실제 실행 결과를 기록하며 모든 장비에서의 성능 보증을 뜻하지 않는다.

## 환경

- Windows 11 x64, 빌드 26200.
- Intel Core Ultra 5 226V, 8코어, Intel Arc 130V, 메모리 약 16GB.
- Python 3.12.14, PySide6/Qt 6.11.2, FFmpeg CLI 9.0.2, PyInstaller 6.22.3.
- 나머지 버전은 constraints.txt 참조. Qt Multimedia 내부 FFmpeg와 CLI FFmpeg는 별개다.
- 자동 UI 검증에는 Qt offscreen 플랫폼과 시스템의 맑은 고딕을 사용했다.

## 수정 및 회귀 검증

| 문제 | 반영 및 확인 |
|---|---|
| 양수 오프셋의 잘못된 첫 장면 | 입력 PTS 정규화 후 지연. 빨강→파랑 영상으로 시작 전 배경과 지연된 장면 확인 |
| 음수 오프셋·짧은 잔여 구간 | 앞부분 자르기, 마지막 프레임 위치를 내림 처리. 1ms만 남는 입력도 마지막 장면 출력 |
| 종료 지점 탐색 화면 잔류 | 재생 상태와 무관하게 위치 적용. 실제 Qt 디코더의 빨강→파랑 전환 확인 |
| 재생 전 빈 미리보기 | 일시정지 상태에서도 첫 프레임을 디코딩하도록 준비 |
| 플레이어 정리 후 앱 종료 | 입력과 콜백을 해제한 후 플레이어·출력·sink 정리. 연속 재생·원본 재연결 확인 |
| FPS·인코더 선택 유실 | 검증된 설정을 즉시 프로젝트와 변경 상태에 반영하고 저장·복원 확인 |
| 이전 프로젝트의 분석 결과 유입 | 작업 세대 구분·취소. 중복 제거, 선택 순서 유지, 최대 2개 동시 분석 확인 |
| 평균 FPS 0/0 | 유효한 대체 FPS 사용, 누락·잘못된 길이는 오류 처리 |
| export의 고정 타임코드 | 공통 Qt 렌더러의 시간별 RGBA 프레임을 작업 스레드에서 전달 |
| 디자인 변경 시 재생 재설정 | 소스·시간 설정과 디자인 변경 분리. 재시작·탐색이 발생하지 않는지 확인 |
| 다중 로딩 시 탐색 반복 | 로딩된 플레이어만 위치를 맞추고 자동 보정 간격을 250ms 이상으로 제한. 사용자 탐색은 즉시 적용 |
| 긴 한글 이름표 | 글꼴 측정과 현재 이름표 이미지 캐시, 셀 내부 말줄임 확인 |
| 취소·쓰기 실패 | 프로세스 종료 후 임시 파일 정리. 기존 출력 보존 및 완료 신호 중복 방지 확인 |

영상·오디오·이름표의 원본 시각은 공통 타임라인에서 계산한다. 프로젝트 JSON 버전 1, 솔로 보기, 매크로, 글꼴 선택 및 CPU/NVIDIA/Intel 인코더 선택은 유지했다.

## 자동 검사와 독립 설치

개인 test_assets와 기존 개발 캐시를 제외한 소스를 별도 디렉터리에 복사하고 새 가상환경에 --no-cache-dir, constraints.txt로 설치했다. FFmpeg는 검증된 원본 ZIP의 체크섬을 확인한 뒤 준비했다.

- 전체 기본 테스트: **82 passed, 1 skipped** (12.35초). 건너뛴 항목은 명시적으로 선택하지 않은 개인 영상 검사 하나다.
- 원본 두 영상을 사용하는 선택적 검사: **1 passed**.
- Ruff 검사·포맷 검사 통과, pip check 통과.
- 새 환경에서 앱 실행, 24/30fps의 가로·세로 합성 영상 두 개 미리보기, 한글 이름표·동적 타임코드·오디오를 포함한 MP4 생성 통과.
- 기존 36개 테스트의 동작을 유지하며 합성 fixture 기반 검증과 회귀 사례를 추가했다.

실제 MP4에서 1·2·3·5·9개 배치, 혼합 FPS·길이·비율, 회전 정보, 해상도·FPS·길이·오디오를 확인했다. 양수·음수 오프셋과 장면 전환 경계는 출력 한 프레임 범위에서 검사했다. 오디오 시작 전·종료 후 무음, 짧은 영상의 마지막 프레임 유지, 시간별 이름표 이미지와 Qt 렌더러의 차이도 검사했다.

회전 테스트 입력은 FFmpeg의 [display_rotation 옵션](https://ffmpeg.org/ffmpeg.html#Video-Options)으로 만들고, 회전 후 실제 출력의 상하 색상 분리를 확인한다.

## 렌더링 비교

같은 프로세스에서 수정 전 렌더러와 수정 후 캐시 렌더러를 번갈아 측정했다. 1920×1080 캔버스, 영상별 320×180 고정 프레임, 맑은 고딕 정적 이름표, 테두리 조건이다. 경로별 600개 표본이며 준비 구간을 제외했다.

| 영상 수 | 전체 그리기 중앙값: 전 → 후 | p95: 전 → 후 | CPU ms/프레임: 전 → 후 |
|---|---|---|---|
| 2 | 1.716 → 1.473ms | 2.128 → 1.848ms | 2.474 → 2.214 |
| 5 | 4.212 → 3.789ms | 5.660 → 5.588ms | 4.922 → 4.323 |
| 9 | 6.171 → 5.500ms | 9.255 → 9.079ms | 7.734 → 7.188 |

전체 그리기 중앙값이 약 10~14% 감소했다. 장식만 그리는 중앙값은 각각 0.310→0.113, 0.563→0.399, 1.354→0.619ms다. 샘플링한 프로세스 작업 집합은 55.4~56.4MiB였다. 두 렌더러가 같은 프로세스에 존재하므로 독립적인 메모리 절감 비교로 해석하지 않는다.

이 측정은 디코딩과 창 크기 변경을 포함하지 않는다. 동적 이름표, 고해상도 입력, 다른 장비의 성능을 대신하지 않는다. 재현 도구는 scripts/benchmark_render.py이며 --baseline에 변경 전 renderer.py를 지정하면 두 경로를 비교한다. 원시 결과는 Git에서 제외되는 artifacts/render-benchmark.json에 보관한다.

## 실제 재생 및 EXE

320×180 H.264·30fps·15초 합성 영상을 독립 디코더로 재생했다. 프레임 PTS와 공통 시각을 약 50ms마다 비교하고 첫 1초를 제외했다. 아래는 최종 코드에서 `--software-decode`를 사용한 약 5초 측정 결과다. UI 그리기는 포함하지 않는다.

| 영상 수 | 준비된 영상 | 시간 오차 중앙값 / p95 / 최대 | 영상 사이 최대 차이 | CPU(한 코어 기준) | 작업 집합 최대 |
|---|---|---|---|---|---|
| 2 | 2/2 | 9.3 / 26.7 / 30.3ms | 0.0ms | 6.8% | 93.6MiB |
| 5 | 5/5 | 12.0 / 31.0 / 37.0ms | 33.3ms | 19.9% | 142.1MiB |
| 9 | 9/9 | 15.3 / 41.7 / 57.0ms | 66.7ms | 30.2% | 208.2MiB |

이 조건에서는 100ms 목표를 만족했다. 반면 기본 자동 하드웨어 디코딩의 9개 측정에서는 9개 프레임이 준비되었지만 표본이 9개에 그쳤고 최대 약 11.8초 지연이 발생했다. 이 장비의 offscreen 검증 조건에서 기본 경로가 안정적이라고 판단할 수 없다. 디코더·드라이버의 정확한 원인은 확정하지 않았으며, 소프트웨어 경로를 검증된 대안으로 제공한다. 큰 영상에서의 소프트웨어 성능까지 보장하지 않는다.

재현 명령:

~~~powershell
python scripts/benchmark_playback.py --software-decode
python scripts/benchmark_playback.py --counts 9 --output artifacts/playback-auto-nine.json
~~~

소프트웨어 옵션은 Qt의 [디코딩 백엔드 설정](https://doc.qt.io/qt-6/advanced-ffmpeg-configuration.html)을 사용한다. 이 설정은 Qt 비공개 설정 API이므로 Qt 버전을 올릴 때 재검증한다. 별도 FFmpeg export 인코더에는 영향을 주지 않는다.

단일 EXE만 둔 별도 폴더에서 PATH를 Windows 시스템 디렉터리로 제한하여 실행했다. 원본 두 개는 기본 재생으로, 합성 영상 아홉 개는 소프트웨어 재생으로 검사했고 모두 프레임 준비와 MP4 저장에 성공했다. 번들 임시 경로의 FFmpeg·FFprobe 사용, 한글·동적 이름표, 640×360·30fps 출력과 선택한 AAC 오디오를 확인했다. 새 Windows VM에서 Python을 제거한 검증은 수행하지 않았으며, 같은 PC에서 경로를 격리한 검사다.

- 라이선스 정리 전 빌드 결과: dist/SyncView.exe, 133,354,615바이트.
- SHA256: 12de52fe089285ab88a3307e604ffbc937d1d8cfb1b77561e6843f3306eb87f6.
- wheel에도 패키지 내부 logo.png·logo.ico 두 리소스가 포함되는지 확인했다.
- 검증용 실행 옵션: `SyncView.exe --verify-project <프로젝트.json> --verify-output <결과폴더>`. 소프트웨어 경로는 `--software-decode`를 함께 지정한다. 이 모드는 미리보기 이미지, MP4와 verification.json을 생성하고 종료한다.

## 라이선스·README 변경 검증 (2026-09-22)

- 전체 테스트: **82 passed, 1 skipped**. Ruff 검사와 포맷 검사를 통과했다. 이번 변경에 성능 재측정은 포함하지 않는다.
- Python wheel의 `License-Expression: MIT`와 라이선스 파일 10개를 확인했다. 실행 파일·개인 영상은 wheel에 포함되지 않는다.
- 수정한 spec으로 EXE를 다시 빌드했다. 최종 CArchive 항목 225개에서 `virtualkeyboard` 관련 DLL·플러그인이 없고, MIT·외부 고지·주요 라이선스 원문이 포함됨을 확인했다.
- 새 EXE 크기: **133,234,596바이트**. SHA256: `dab4d558b09e3a696aec503c813b9b95d5979f24eff202e70ccd2ef1167ee694`.
- EXE만 복사한 별도 폴더에서 PATH를 Windows 시스템 경로로 제한하고 Python 환경 변수를 제거했다. `--software-decode`와 offscreen 검증 모드로 합성 영상 4개 프레임을 확인했으며, 번들 FFmpeg·FFprobe로 H.264·1280×720·30fps·약 5.266초 MP4를 저장했다. 새 Windows VM 검증이나 바이너리 공개 배포는 수행하지 않았다.
- 한국어·영어 README의 로컬 링크와 이미지 경로를 확인했다. 스크린샷은 실제 앱에서 합성 영상 4개를 재생한 결과이며 개인 영상은 사용하지 않았다.

이 실행 검증은 EXE 재배포 조건을 모두 충족했다는 뜻이 아니다. 대응 소스·전체 구성요소 고지·Qt 재결합 절차의 남은 준비는 [라이선스 검토](LICENSING.md)를 따른다.

## 한국어·영어 UI 및 포터블 검증 (2026-09-22)

- 전체 테스트: **92 passed, 1 skipped**. 기존 82개에 언어 선택·저장·시스템 언어 fallback·전환 중 상태 보존·도움말·Qt 기본 버튼·오류·번역 카탈로그·export 취소 판정 검증을 추가했다. Ruff 검사와 포맷 검사도 통과했다.
- 한국어·영어 실제 UI를 합성 영상 네 개로 확인했다. 언어를 바꿔도 원본 이름표·매크로·위치 enum·오디오·인코더·프로젝트 변경 여부·재생 상태가 유지된다. 영어 설정 패널은 좁은 폭에서 긴 행을 줄바꿈한다.
- `scripts/build_portable.ps1`로 ZIP을 생성했다. 앱 소스 스냅샷, 외부 고지와 주요 라이선스, `qtbase_ko.qm`, 빠른 시작 안내, 소프트웨어 디코딩 실행 파일을 포함한다. 최종 ZIP에서 Virtual Keyboard 제외와 231개 파일 해시를 확인했다. ZIP 체크섬은 `dist/SyncView-windows-x64-portable.zip.sha256`에 기록한다.
- ZIP을 한글·공백 경로에 압축 해제하고 PATH를 Windows 시스템 경로로 제한했다. `PYTHONHOME`, `PYTHONPATH`, `VIRTUAL_ENV`를 제거한 뒤 영어·한국어 각각 `--software-decode`로 영상 4개 프레임과 H.264·1280×720·30fps·약 5.266초 MP4 출력을 확인했다. 같은 PC에서의 offscreen 검사이며 새 Windows VM 검증은 아니다.
- 단일 EXE의 첫 검증에서 1.5초 안에 프레임이 준비되지 않아 실패했으나 같은 실행 파일의 재시도는 성공했다. 검증 모드를 고정 대기 후 실패하는 방식에서 모든 프레임 준비 후 export하는 방식으로 수정했다. 전체 120초 제한은 유지한다.
- 수정 후 최종 단일 EXE도 별도 폴더와 제한된 PATH에서 영어 UI·영상 4개 미리보기·MP4 출력에 성공했다. 크기는 133,253,398바이트, SHA256은 `ab9927b221e6d5aaa517c0351ec97296b74ef456b0a1ae5aeed2886ba5f7c07c`다.
- Qt 번역 파일은 [Qt Translations 6.11.2의 파일별 규칙](https://github.com/qt/qttranslations/blob/v6.11.2/licenseRule.json)에 따라 LGPLv3 경로로 취급한다. 공개 바이너리 배포를 위한 전체 대응 소스·고지 준비는 여전히 별도 작업이다.

## 1.1.0 소스 태그 검증 (2026-09-22)

- 언어 선택과 포터블 패키징은 호환되는 기능 추가이므로 MINOR를 올려 1.1.0으로 정했다. 앱 버전 두 곳을 일치시키고, 프로젝트 JSON 스키마는 버전 1을 유지했다. 버전 규칙은 `AGENTS.md`, 변경 사항은 `CHANGELOG.md`에 기록했다.
- 전체 테스트를 다시 실행해 **92 passed, 1 skipped**를 확인했다(15.36초). 제외된 항목은 개인 영상 선택 테스트다. Ruff 검사·포맷 검사와 `git diff --check`를 통과했다.
- 네트워크 없이 wheel을 생성해 패키지 메타데이터와 런타임 버전이 모두 1.1.0임을 확인했다. MIT 메타데이터·로고 리소스를 포함하며 실행 파일·개인 영상은 포함하지 않는다.
- Git 추적 대상에서 빌드 결과·개인 영상·캐시가 제외되고, README 두 언어와 기여 지침·변경 이력의 로컬 링크가 유효함을 확인했다.
- 이번 버전 확정에서는 소스·wheel을 재검증했으며 EXE·ZIP을 다시 빌드하거나 공개하지 않았다. 위 실행 검증과 해시는 버전 변경 전 빌드 결과다.

## 남은 범위

- NVIDIA/Intel 하드웨어 인코더의 실제 장비별 성공 여부와 속도는 별도 검증 대상이다. 이번 실제 export 검증은 CPU libx264를 사용했다.
- 기본 하드웨어 미리보기 경로의 9개 동시 재생은 안정성 기준을 충족하지 못했다. 기준 장비에서는 소프트웨어 옵션을 사용한다.
- 고해상도 9개 입력의 장시간 재생, 가변 프레임률·손상 파일의 모든 변형, 모든 글꼴·코덱 조합은 검증하지 않았다.
- 100ms 동기 목표는 측정 조건에 한정한다. 프레임 단위 분석 기능이나 모든 입력에 대한 시간 정합 보증은 아니다.
- 이 구현 검증을 진행할 당시 작업 경로에 .git 이력이 없어 기존 추적 파일 변경 여부나 이전 커밋 이력은 확인할 수 없었다. 이후 GitHub 업로드 이력은 [SyncView 커밋 목록](https://github.com/Rainbow-Tools/SyncView/commits/main/)에서 확인한다.
